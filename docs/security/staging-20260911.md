- Access token con durata 900 secondi; rotazione refresh token attiva.
- Utenti anonimi e collegamento manuale identità disabilitati.

Per evitare invii non richiesti, disabilitati **solo nello staging** i trigger `messages_notify_trigger`, `friendships_notify_trigger`, `user_matches_notify_trigger`, `live_messages_notify_trigger`. Verificati zero job in `cron.job`. Le policy, i trigger di sicurezza e le publication Realtime restano attivi. Gli account di prova sono sintetici, confermati con admin API senza inviare email, e rimossi dagli script al termine.

## Risultati e limite Auth bloccante

- **41/41** verifiche HTTP API/Edge Functions: `staging-http-20260911.jsonl`.
- **3/3** verifiche Realtime via WSS: `staging-realtime-20260911.jsonl`.
- **21/21** asserzioni pgTAP sul database cloud: `staging-pgtap-20260911.txt`.
- Auth/Storage: i test di hash bcrypt, password corta, upload validato, logout locale/globale, JWT revocati e refresh token sono passati; il blocco dei tentativi password è fallito.

Supabase ha rifiutato con **HTTP 402** l'attivazione sia di `hook_password_verification_attempt_enabled`, sia di `password_hibp_enabled`: queste funzioni non sono disponibili sul piano Free dell'organizzazione. Non è stato attivato alcun piano a pagamento. La funzione SQL esiste nel database, ma **il servizio Auth cloud non la invoca**.

Evidenza: 35 tentativi errati consecutivi sul medesimo account sintetico restituiscono tutti `400`, senza `429`. Questa prova non dimostra assenza di ogni limite IP/provider, ma dimostra che il blocco per account richiesto non è operativo. CAPTCHA non configurato. Le impostazioni effettive sono in `staging-auth-config-20260911.json`.

La prima esecuzione (`staging-auth-storage-20260911.jsonl`) ha osservato un `429` su un successivo login corretto e un `200` dopo la query di scadenza simulata. **Non costituiscono prova del lockout SQL**, perché l'hook non è attivo. Il test è stato migliorato per verificare prima l'esistenza del contatore per account; il retest `staging-auth-storage-retest-20260911.jsonl` segnala come non verificabili i due casi dipendenti quando tale contatore manca. Gli script restituiscono un exit code non-zero se la suite non è interamente superata.

Il retest Auth/Storage conta **11 passati, 1 fallito e 2 non verificabili**. I due ultimi casi non sono successi: dipendono dal lockout per account assente.

La verifica di pulizia ha inoltre rilevato quattro fixture A/B rimaste dalle prove API e Realtime: l'admin delete tenta `ON DELETE SET NULL` sui partecipanti dei messaggi ed è respinto dal trigger di immutabilità. Gli script ignoravano la risposta di errore. Corretto il cleanup per eliminare prima i soli messaggi sintetici della fixture e verificare gli status HTTP della cancellazione. Rimossi gli ID esatti delle quattro fixture; ripetute le suite nei file `staging-http-cleanup-retest-20260911.jsonl` e `staging-realtime-cleanup-retest-20260911.jsonl`. Questa correzione riguarda il test harness: non dimostra il corretto funzionamento del flusso applicativo di cancellazione account con cronologia, da provare separatamente. Il conteggio finale è registrato in `staging-summary-20260911.json`.

Il piano Free basta a proseguire test di isolamento e API, ma questo staging non soddisfa ancora tutti i requisiti Auth. Un eventuale passaggio di piano va deciso esplicitamente: il piano è a livello di organizzazione, che attualmente contiene anche produzione. In alternativa valutare un'organizzazione di staging separata e una protezione equivalente che copra gli endpoint Auth diretti.

## Ripetizione delle prove

Dalla root del repository, con le credenziali locali dello staging presenti:

```bash
VIBRA_PENTEST_STAGING=1 python3 script/security/probe_local.py
VIBRA_PENTEST_STAGING=1 /tmp/vibra-pentest-reverify-venv/bin/python script/security/probe_realtime.py
VIBRA_PENTEST_STAGING=1 python3 script/security/probe_auth_storage.py
supabase test db --linked --workdir "$HOME/.supabase/vibra-staging/workspace"
```

Il virtualenv Realtime usa `websockets==15.0.1`. Senza `VIBRA_PENTEST_STAGING=1`, gli script mantengono il laboratorio loopback originale. Lo staging è vincolato al project ref sopra; `staging_admin.py` rifiuta percorsi Management API di altri progetti. Verificate quattro prove negative di rifiuto target senza chiamate di rete. Per le interrogazioni amministrative il helper usa esclusivamente il token Supabase CLI già presente nel Keychain macOS; non lo stampa né lo copia nei file delle prove.

La CLI ha segnalato un errore nella cache locale del catalogo pg-delta dopo il deploy: migrazioni applicate e cronologia cloud di 44 voci verificate; i test pgTAP cloud sono passati. Non sono stati disabilitati controlli TLS per aggirare quell'avviso.
